# Learning Contract: Work and Communicate Like a Teammate

Student: Neil Pack  
Date: November 5, 2026  
Target assessment date: November 12, 2026

## Primary competency

By the end of this contract, I will be able to:

I can contribute a well-scoped piece of work to a team website, communicate its status and risks, explain an important technical decision, and give or apply actionable review feedback. I can break my part of a new team website into tasks with a clear definition of done, share progress and blockers with my team, record a technical decision with its alternatives and rationale, review a teammate's code in a specific and respectful way, and integrate team changes without lowering the quality of the site.

## Specific slices in this contract

- Breaking work into tasks with a definition of done
- Progress, blocker, and integration communication
- Technical decision records
- Specific and respectful code review
- Integrating team changes while maintaining quality

## My starting point

I already know/can:

I can build a complete website on my own with semantic HTML, responsive CSS, and modular JavaScript. In my hiking guide, I rendered content from data, retrieved information from an API, stored preferences with `localStorage`, connected a list-to-detail flow with URL parameters, and audited the site for SEO and accessibility. I can use Git to commit and push my own work, and I have completed peer reviews in earlier weeks where I explained my code and responded to questions.

I still need to learn or improve:

- How to start a new website with a team instead of building one by myself.
- How to break a feature into small tasks that each have a clear and testable definition of done.
- How to write useful progress updates that name what is finished, what is next, and what is blocking me.
- How to write a short technical decision record that compares alternatives and explains why one was chosen.
- How to give code review feedback that is specific, actionable, and respectful, and how to respond well to feedback on my own code.
- How to use branches, pull requests, and merges so that team changes can be combined safely.
- How to resolve a merge conflict or dependency between my work and a teammate's work without breaking the site.
- How to check that the integrated site still meets our standards for layout, accessibility, and functionality.

## My learning plan

I will use these resources:

- The [WDD 231 Competency Guide](https://byui-cse.github.io/wdd231-course/), class examples, and feedback from my instructor or teaching assistant.
- My teammates, our shared repository, and our team communication channel.
- [GitHub Docs: About issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/about-issues) and [GitHub Docs: About pull requests](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-pull-requests).
- [GitHub Docs: Resolving a merge conflict](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/addressing-merge-conflicts/resolving-a-merge-conflict-using-the-command-line).
- [Architecture Decision Records](https://adr.github.io/) as a guide for writing a short decision record.
- [Google Engineering Practices: Code Review](https://google.github.io/eng-practices/review/) for guidance on giving and receiving review feedback.

I will practice by:

I will work with a team to build a new website that is separate from my hiking guide. This week 8 website will be the place where I show the work for this contract. Our team will agree on the purpose of the site, divide it into features, and assign each feature to a team member. I will take ownership of one well-scoped feature or page and break it into tasks recorded as issues, a task list, or a milestone. Each task will include a definition of done, such as "the section is responsive at mobile and desktop widths, passes a keyboard check, and is merged into the main branch without errors."

I will post short progress updates to my team that describe what I completed, what I plan to do next, and any blockers or dependencies on a teammate's work. When our team makes an important technical choice, such as how to organize the shared CSS, how to structure the JavaScript modules, or how to store and load the site's data, I will write a decision record that lists the options we considered, the choice we made, and why.

I will do my work on a separate branch and open a pull request when it is ready. I will review at least one teammate's pull request and leave feedback that points to specific lines or behaviors, explains the reason for the suggestion, and stays respectful. I will also respond to the review feedback I receive and update my code where it improves the work. When the branches are merged, I will test the combined site, resolve any merge conflict or dependency, and confirm that the site still works and meets our quality standards.

My first milestone, due November 9, 2026, is:

I will help set up the shared repository for the new team website, record my assigned feature as a set of tasks with a definition of done for each one, and post my first progress update to the team. I will also have the first part of my feature committed on its own branch.

## Evidence of learning

I will submit or demonstrate:

- An issue, task list, or milestone for my feature with a clear completion condition for each task.
- A role or contribution summary describing what I built and how my work fits into the team website.
- At least two progress updates that describe completed work, next steps, blockers, or integration risks.
- One technical decision record with the problem, the alternatives considered, the decision made, and the rationale.
- A code review I gave to a teammate and a response to feedback I received on my own pull request.
- Evidence of successful integration, such as a merged pull request and the working team website.
- A description of one merge conflict or dependency I resolved and how I resolved it.
- A short check showing that the integrated site still works, including a responsive layout check, a keyboard check, and no console errors.
- One documented challenge or design decision and what I learned from working as part of a team.

I will know I am ready when:

- My feature was broken into tasks that each had a clear definition of done, and each task was completed and checked against that definition.
- My team received regular updates from me, and any blocker or dependency was communicated before it delayed the project.
- I can explain one important technical decision, the alternatives we considered, and why we chose the approach we did.
- I gave review feedback that was specific, actionable, and respectful, and I applied or responded to the feedback I received.
- My work was merged into the shared website, the combined site works correctly, and I can explain how I resolved at least one conflict or dependency.

## Support and risks

The help I may need is:

I may need help from my teammates to agree on the scope of the website, the division of work, and the standards we will use for a definition of done. I may ask my instructor or teaching assistant for feedback on my decision record or code review, and I may use GitHub documentation when I am unsure how to manage branches, pull requests, or merge conflicts.

A risk to my plan is:

A likely obstacle is that team members may have different schedules, or that one person's work may depend on another person's work that is not finished yet. Two teammates may also edit the same file and create a merge conflict. I will respond by communicating early, keeping my tasks small, pulling the latest changes often, and naming dependencies in my progress updates. If a conflict happens, I will compare both versions carefully, talk with the teammate who made the other change, and test the site after resolving it.

## AI use, if applicable

I expect to use AI for:

I may use AI for explanations of Git branching and merge conflicts, brainstorming how to break a feature into tasks, improving the clarity of my progress updates or decision record, and debugging code in my part of the website. I will write my own code review comments and make the final decisions with my team.

I will verify AI suggestions by:

I will compare suggestions with GitHub documentation, the WDD 231 Competency Guide, and my team's agreed standards. I will test any code change in the integrated website using browser developer tools, a responsive layout check, and a keyboard check. I will discuss suggestions that affect shared code with my team before using them, and I will not count an AI suggestion as evidence until I can explain it and verify that it works.
