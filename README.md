## About This Project

This is a new website that our team is building together from scratch, separate from our individual projects from earlier weeks. Its purpose is to practice the skills professional developers use when they work on a shared codebase. The final product should be a working, responsive, accessible website, and the process we use to build it together matters just as much as the site.

The site is built with semantic HTML, responsive CSS, and modular JavaScript:

```
index.html     Home page
styles/        Shared and page-specific CSS
scripts/       JavaScript modules
docs/          Learning contract, planning notes, and decision records
```

## What We Are Trying to Accomplish

Our goal is to contribute well-scoped work to a shared website, communicate clearly about it, and combine everyone's changes without lowering the quality of the site. Specifically, we will:

1. **Break work into tasks with a definition of done.** We will agree on the site's purpose, divide it into features, and give each teammate ownership of one feature or page. Each feature will be broken into small tasks, tracked as GitHub issues, a task list, or a milestone, and each task will have a clear, testable definition of done.
2. **Communicate progress, blockers, and integration risks.** We will post regular updates that say what is finished, what is next, and anything that is blocked or depends on a teammate's work.
3. **Record technical decisions.** When we make an important choice, such as how to organize shared CSS, structure JavaScript modules, or store and load data, we will write a short decision record that covers the problem, the alternatives we considered, what we chose, and why.
4. **Give and receive specific, respectful code review.** Each feature will be built on its own branch and submitted as a pull request. We will review each other's pull requests with feedback that points to specific lines or behaviors and explains the reasoning, and we will respond to and apply the feedback we receive.
5. **Integrate changes while maintaining quality.** After merging, we will test the combined site, resolve any merge conflicts or dependencies, and confirm that it still meets our standards.

## Definition of Done (Team Standard)

A task is done when it:

- Is responsive at mobile and desktop widths
- Can be fully used with a keyboard
- Produces no console errors
- Has been reviewed through a pull request and merged into `main` without breaking the site

## Workflow

1. Pick up a task from the issues or task list.
2. Create a branch for the task.
3. Commit and push your work to that branch.
4. Open a pull request and request a review from a teammate.
5. Address the review feedback.
6. Merge into `main`, pull the latest changes, and test the integrated site.

## Evidence of Learning

As we work, this repository will collect evidence for the Week 8 learning contract, including:

- Issues or milestones with clear completion conditions
- Progress updates
- A technical decision record
- Code review comments and responses
- Merged pull requests and a description of a resolved merge conflict or dependency
- A final check of the integrated site (responsive layout, keyboard navigation, and no console errors)
